BeerFest 促销智能问数

设计方案预览 — 让运营人员用自然语言查询促销数据

1. 问题与目标

当前痛点：运营人员需要查具体数据时，必须手动翻 dashboard 或写 SQL，效率低、门槛高。

目标：运营人员用自然语言提问（"满200减50核销了多少张""昨天营收最高的券是哪个"），系统自动理解意图、查询数据库、返回精确数字 + 可视化。

核心思路：LLM 不直接生成 SQL，而是从一组预定义的安全查询模板中选择最匹配的，并提取参数（券种名、金额阈值、数量等）。SQL 由开发者编写和审核，LLM 只负责"路由 + 填参 + 生成回答文案"。

8. 风险与对策

LLM 意图分类不准 风险

LLM 可能选错模板或参数提取错误

对策：模板选择走结构化 JSON 输出 + Schema 校验；参数提取失败时返回澄清问题而非错误数据；fallback 回通用 Ops Chat

查询模板不够用 风险

运营问的问题不在 8 个模板覆盖范围内

对策：模板设计为开放式扩展；未匹配时 fallback 到通用 Ops Chat + 记录日志分析高频问题

DeepSeek 稳定性 风险

LLM 偶发波动，JSON 格式不严格

对策：复用 sanitizeLLMJSON 三层防御；关键查询模板加规则引擎兜底（关键词直接匹配）

9. 方案优势

安全 关键

LLM 不接触 SQL 生成，只选模板 + 填参数。所有 SQL 由开发者编写和 review，杜绝注入风险。参数化查询 + 只读账号。

准确

SQL 模板经过验证，数据结果可预期。LLM 只负责"翻译"——将自然语言映射到已知查询，而非凭空生成。

渐进式

V1 上 8 个高频模板覆盖 80% 场景。发现新需求时新增模板（仅后端加一个 SQL + 描述），无需改动架构。

低成本

每次查询 1 次 LLM 调用（~500 tokens），与现有 Ops Chat 成本相同。不需要额外基础设施。

10. 与现有 Ops Chat 的关系

维度现有 Ops Chat新增智能问数

能力固定指标概述 + 策略建议任意维度精确查询 + 对比/排名/异常检测
输出JSON 报告或纯文本NL 回答 + 结构化数据 + 图表
典型问题"当前营收和核销率如何""全场8折发了多少张，核销多少"
关系互补：Ops Chat 做宏观概览 + 策略建议；智能问数做微观精确数据查询。两者共用一个 Chat UI，根据问题类型自动路由。
