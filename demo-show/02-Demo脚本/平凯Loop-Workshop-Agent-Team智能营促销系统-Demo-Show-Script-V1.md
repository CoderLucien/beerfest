# 平凯 Loop Workshop：体验 Agent Team 带来的高效开发方式

## 啤酒节智能营促销系统 Demo Show Script V1

建议时长：标准版 32—35 分钟，可裁剪为 25 分钟  
演示方式：主持人兼业务负责人 1 人，Loop 操作员 1 人；也可由同一人完成  
业务性质：场景化演示，不代表国际啤酒节官方系统  
数据边界：客流、订单、库存和经营结果均为合成数据；Loop 任务、代码变更、测试和耗时为现场实际结果

> 使用说明：`【口播】`内容可以直接讲；`【屏幕】`、`【操作】`、`【观察点】`和`【兜底】`不需要念出。Loop 的按钮名称和 Agent Team 操作方式以活动环境实际版本为准，彩排时应替换为准确 UI 文案。

## 0. 这场 Demo 要证明什么

全场只证明一个核心观点：

> **Loop 不只是让一个 Agent 更快写代码，而是把产品、数据、前端、后端和测试组织成一个能够分工、协作、验收并持续迭代的 Agent Team。**

观众离场前应记住五个 Agent Team 提效点：

1. **需求结构化**：把一句模糊业务要求转成用户故事、任务和验收标准；
2. **并行开发**：可并行的页面、数据、接口和测试同时推进，缩短墙钟时间；
3. **共享交付物**：Agent 围绕同一个 Workspace、接口契约和业务对象工作，减少复制粘贴和上下文丢失；
4. **独立验收**：测试 Agent 依据原始验收标准检查结果，不让“写代码的人自己宣布成功”；
5. **连续迭代**：第一次发布后，Agent Team 能在原有代码、规则、测试和上下文上完成第二次变更。

全场同时展示两条闭环：

- **Loop 研发闭环**：需求 → 分工 → 并行开发 → 集成测试 → 发布 → 变更 → V2；
- **系统经营闭环**：发现问题 → 生成促销 → 规则校验 → 人工审批 → 执行 → 暂停 → 评估。

前一条证明 Loop 的交付效率，后一条证明大家为什么值得开发这套系统。

## 1. 舞台与环境准备

### 1.1 屏幕布局

建议只在三个视图之间切换：

1. **Loop Agent Team 工作台**：任务、Agent、进度、代码 Diff 和测试；
2. **运营驾驶舱**：客流、排队、库存、预算、活动建议与审批；
3. **游客端 H5**：活动推荐、领券和模拟下单。

不要长时间展示终端滚屏。必须展示终端时，只保留当前命令、关键测试结果和实际耗时。

### 1.2 预置内容

现场应主动说明以下内容已经预置：

- 登录、导航、基础 UI 设计系统；
- Loop Workspace 和可运行项目骨架；
- TiDB 演示数据库连接；
- 10,000 个游客会话、12 个模拟商户、48 个商品和 600 笔历史订单；
- 客流、排队、库存和订单事件生成器；
- 支付、消息、地图和 POS 模拟适配器；
- V0 稳定 Checkpoint 和失败兜底版本。

现场实际由 Agent Team 完成或修改：

- 经营需求和验收标准；
- 活动、审批和实验相关数据模型；
- 智能促销建议与审批工作流；
- 运营驾驶舱核心模块；
- 领券幂等、预算和库存约束；
- 自动化业务测试；
- 第二轮客群资格规则变更。

### 1.3 Agent Team 角色

| Agent | 职责 | 主要产物 |
|---|---|---|
| Team Lead / 需求 Agent | 理解业务、控制范围、拆任务、处理依赖 | 用户故事、任务图、验收标准、发布结论 |
| 数据与工作流 Agent | 业务对象、状态机、事务和 API | Schema、迁移、接口、审批与暂停工作流 |
| 前端体验 Agent | 运营驾驶舱和游客端体验 | 页面、组件、交互与接口接入 |
| 测试评估 Agent | 根据验收标准独立验证 | 自动化测试、问题单、回归结论 |

如果现场版本支持更多 Agent，可把数据和后端拆开，但舞台上不建议同时展示超过 5 个角色。

## 2. 标准版逐字脚本

## 第一幕｜我们今天不演示“AI 写一个页面”

建议时间：0:00—2:30

### 2.1 开场

【屏幕】标题页：**平凯 Loop Workshop：体验 Agent Team 带来的高效开发方式**

【口播】

大家好，欢迎来到平凯 Loop Workshop。

今天我们不准备花半个小时介绍 Agent Team 的概念，也不准备只让大家看一个 Agent 生成几个页面。

我们会把一个真实感很强、但范围可控的业务需求，现场交给 Loop 里的 Agent Team。大家会看到：它怎样理解需求、怎样分工、怎样并行开发、怎样相互交付，最后怎样通过测试形成一个可以运行的版本。

更重要的是，第一次上线以后，我们还会临时改变业务规则，再看这个 Team 能不能基于已经形成的代码、数据模型和测试继续迭代。

[停顿]

所以今天真正要观察的不是代码生成速度，而是一个 Agent Team 能不能完成一条完整的软件交付链。

### 2.2 透明说明演示边界

【屏幕】一页三栏：预置 / 现场生成 / 模拟数据。

【口播】

在开始之前，我先把演示边界讲清楚。

登录、导航、UI 骨架、数据库连接和外部系统模拟器已经预置。客流、订单和经营结果使用合成数据。

今天现场实际完成的是业务需求拆解、核心数据模型、促销审批工作流、运营页面、业务测试，以及第二轮规则变更。Loop 产生的任务、代码 Diff、测试结果和时间都是现场真实记录。

我们不会把模拟经营结果说成客户 ROI，也不会把预置骨架说成现场从零生成。

【观察点】

- 主持人一开始就建立可信边界；
- 后续任何页面上的经营数字都有“模拟数据”标识。

## 第二幕｜给 Agent Team 一个真正需要协作的业务任务

建议时间：2:30—6:00

### 2.3 业务背景

【屏幕】显示啤酒节经营场景图：A 区、B 区、商户、游客、订单、库存。

【口播】

我们把场景放在啤酒节。

公开数据显示，2025 年国际啤酒节西海岸会场 30 天接待游客 697 万人次，崂山会场接待游客 78 万人次。这样的活动并不只是“流量很大”，而是客流、商户、商品、库存、活动和现场服务在不断变化。

今天我们不是开发一个普通领券页面，而是开发一套“啤酒节智能营促销系统”。

它需要看见经营问题，生成受预算和库存约束的促销方案，经过人的审批后执行，再用实验组和对照组判断这次优惠到底创造了增量，还是仅仅给原有订单打了折。

### 2.4 主经营事件

【屏幕】驾驶舱静态 Brief，显示四个数字。

【口播】

现在，演示时间来到晚上七点半。

A 区热门摊位平均等候时间已经达到二十二分钟；相邻 B 区的客流比同时间段基线低百分之三十五；B 区还有四百二十份餐饮文创组合需要改善周转；当前活动预算只剩六千元。

业务负责人提出的要求是：

“不要全场无差别打折。请面向合适客群设计一个错峰促销，让部分客流去 B 区，同时守住预算、库存和人群资格边界，并且告诉我活动是否真的产生了增量。”

这是一句话，但背后同时包含产品、数据、前端、后端、工作流、风控和测试。它非常适合检验：一个 Agent Team 到底是不是一个 Team。

### 2.5 启动现场计时

【操作】在计分板记录 Brief 确认时间，启动墙钟计时。

【口播】

从现在开始计时。我们不会预先承诺几分钟交付，最后只看现场实际结果。

## 第三幕｜Loop 先把模糊需求变成共同计划

建议时间：6:00—9:00

### 2.6 向 Loop 提交主任务

【屏幕】Loop 新任务输入框。

【操作】粘贴以下主 Prompt。彩排时根据实际项目路径和命令补全，不要临场改写。

```text
请使用 Agent Team，在现有 beerfest-growth Workspace 中交付“啤酒节智能营促销系统”P0 版本。

业务事件：
- A 区平均排队 22 分钟；
- B 区客流低于同时间段基线 35%；
- B 区餐饮文创组合库存 420 份；
- 剩余促销预算 6000 元。

系统需要：
1. 在运营驾驶舱展示区域客流、排队、库存、订单和预算；
2. 生成“夜游错峰组合券”草案，包含目标客群、商品、满 88 减 12、最多 500 张、90 分钟有效期；
3. 草案必须经过人工审批，未审批不得发布；
4. 发券时校验资格、重复领取、预算和库存；
5. 库存低于 80、退款率超过 3% 或预算耗尽时自动暂停；
6. 使用实验组与对照组展示转化、净支付 GMV 和优惠成本；
7. 页面标注“模拟数据，不代表真实经营结果”。

请由 Team Lead 先输出：
- P0 范围和明确不做的内容；
- 用户故事与可执行验收标准；
- Agent 分工、依赖和交付顺序；
- 需要人工确认的关键决策。

确认计划后，由数据与工作流、前端体验、测试评估 Agent 协作实现。任何 Agent 不得自行降低验收标准；关键发布必须等待人工批准。
```

### 2.7 讲解 Team Lead 的价值

【屏幕】展示 Team Lead 生成的任务树，不需要逐字阅读全部内容。

【口播】

这里第一个提效点并不是开始写代码，而是先把模糊需求变成团队共同使用的任务和验收标准。

大家可以看，Team Lead 没有把一句话直接扔给某个 Coding Agent。它先明确 P0：我们做驾驶舱、活动草案、审批、发券约束、自动暂停和效果评估；真实支付、跨商户结算、生产级推荐模型不在今天范围内。

范围收敛以后，数据与工作流 Agent 可以先定义活动状态和接口；前端 Agent 可以基于同一份契约开发页面；测试 Agent 从一开始就拿到验收标准，而不是等代码写完以后再猜“什么算做完”。

这一步减少的是传统协作里最常见的返工：大家都很忙，但每个人理解的需求并不相同。

【操作】人工确认计划，允许 Agent Team 进入执行。

【口播】

计划没有替人做最终决定。范围和关键约束确认以后，我们再让 Team 开始执行。

## 第四幕｜Agent Team 并行开发，但不是各写各的

建议时间：9:00—16:00

### 2.8 展示并行任务

【屏幕】Loop Agent Team 任务视图，展示三个并行分支：数据与工作流、前端体验、测试准备。

【口播】

现在进入第二个提效点：并行。

数据与工作流 Agent 正在定义 Campaign、Campaign Version、Approval、Coupon、Experiment Assignment 和 Workflow Instance；前端 Agent 在搭运营驾驶舱和审批界面；测试 Agent 不需要等到最后，它可以先根据验收标准准备场景测试和测试数据。

这里要强调，并行不等于简单地多开几个 Agent。

真正的 Team 必须知道谁依赖谁。前端需要数据 Agent 给出的字段和状态；测试需要使用同一组业务规则；如果接口契约变化，受影响任务必须能够收到变化，而不是靠人把一段聊天复制给另一个 Agent。

### 2.9 展示共享产物和 Handoff

【屏幕】打开数据与工作流 Agent 交付的简化对象/接口契约，再切到前端 Agent 已引用的相同字段。

【口播】

这是第三个提效点：共享交付物。

数据 Agent 交付的不只是一段解释，而是可被其他 Agent 消费的 Schema、迁移和接口契约。前端使用的是同一份活动状态和预算字段，测试也基于同一份停止条件生成用例。

这使得交接从“我告诉你我做了什么”，变成“我的产物已经成为你下一步工作的输入”。

### 2.10 在等待期间解释“为什么不用一个大 Agent”

【屏幕】保持任务视图，突出各 Agent 的当前任务、已完成产物和阻塞关系。

【口播】

大家可能会问：这些事情能不能全部交给一个更强的 Agent？

当然可以让一个 Agent 顺序完成，但任务一长，它需要同时记住产品目标、数据库结构、接口、页面、测试和发布约束。上下文越来越长以后，遗漏和自我确认的风险也会上升。

Agent Team 的价值不是模型数量越多越好，而是把可以并行的工作并行，把需要串行的依赖明确下来，再让一个相对独立的角色做验证。

最后我们也不会用 Agent 数量证明提效。真正有意义的是：墙钟时间缩短了多少，多少验收项一次通过，发生了几次人工修复。

### 2.11 展示一次真实问题处理

【操作】如果测试 Agent 发现问题，优先展示真实问题，例如重复领券、未审批活动可见或库存阈值边界错误。

【口播——有真实问题时】

这里测试 Agent 发现了一个问题：`[按现场结果描述]`。

这反而是一个很重要的 Team 信号。写代码的 Agent 没有自己宣布完成，测试 Agent 按最初的验收标准把问题退回给了责任 Agent。Loop 保留了问题、修改和复测之间的关系。

提效不是永远不出错，而是错误更早暴露、责任更清楚、修复后能够自动回归。

【口播——首轮无问题时】

这一轮所有 P0 用例首轮通过。我们仍然保留独立测试步骤，因为“这次没发现问题”不等于可以让开发 Agent 跳过验证。

【兜底】

如果 Agent 运行时间超出彩排窗口，切换到最近的真实 Checkpoint，并明确口播：“为了不让大家等待，我们切换到彩排中同一任务产生的 Checkpoint；后面的审批、运行和第二轮变更继续现场执行。”不要把 Checkpoint 说成刚刚生成的结果。

## 第五幕｜测试不是结束，测试是发布门

建议时间：16:00—19:00

### 2.12 查看验收结果

【屏幕】测试评估 Agent 的结构化结果：通过项、失败项、修改记录、未覆盖风险。

【口播】

现在进入第四个提效点：独立验收。

我们不看“代码生成成功”这句话，而看最初定义的业务条件有没有成立。

未审批活动是否对游客不可见？同一个用户重复请求会不会收到两张券？预算和库存是否一起校验？库存降到八十以下以后会不会自动暂停？页面有没有明确标注模拟数据？

只有这些条件通过，V1 才算完成。

【操作】展示测试通过结果；记录通过数。进入人工发布门。

### 2.13 人工批准 V1

【口播】

Agent Team 可以完成大量执行工作，但发布仍然是一个明确的人类决策点。

现在我们确认范围、测试和风险说明，批准 V1 发布。

【操作】批准发布，打开预览地址；记录 V1 可访问时间。

【屏幕】先展示运营驾驶舱，再快速展示游客 H5。

【口播】

到这里，我们得到了第一版可运行系统。请注意，我们记录的是从 Brief 到可访问版本的真实墙钟时间，而不是把几个 Agent 的耗时简单相加后宣布效率提升。

## 第六幕｜让系统完成一次真实感的经营工作流

建议时间：19:00—25:00

### 2.14 播放晚高峰事件

【屏幕】运营驾驶舱；启动固定种子的事件流。

【口播】

现在应用开发完成，但业务还没有完成。

我们把时间推进到晚高峰。大家看到 A 区排队上升，B 区客流下降，餐饮文创组合库存偏高。系统根据实时状态生成了一份“夜游错峰组合券”草案。

### 2.15 查看 Agent 建议

【屏幕】展开促销建议卡。

【口播】

这里的 Agent 不是只写了一句“建议发券”。

它给出了目标客群、满八十八减十二、最多五百张、六千元预算上限和九十分钟有效期；同时给出了三条停止条件：库存低于八十、退款率超过百分之三，或者预算耗尽。

更重要的是，系统告诉审批人：为什么现在要行动、使用了哪些数据、哪些人不能触达，以及最后如何通过实验组和对照组判断增量。

【互动口播】

如果大家是现场经营负责人，看到这张卡会直接让 Agent 发布吗？

[停顿，观察现场]

我们的答案是：不能。Agent 可以生成方案，但改变真实业务状态以前，必须经过资格、预算、库存和人的审批。

### 2.16 审批并执行

【操作】查看规则校验结果，点击批准；切到游客端演示一位符合资格的用户领券和模拟下单。

【口播】

现在我们批准这次活动。

系统冻结当前活动版本，分配实验组和对照组，占用预算和可售券额度。符合资格的游客可以在 H5 看到推荐；对照组不会收到优惠，但仍然记录同期行为。

这使得我们最后能够回答：增长是活动带来的，还是晚高峰本来就会发生。

### 2.17 触发自动暂停

【操作】推进事件流，使可售组合库存降至阈值以下，或者触发预置退款率异常。

【屏幕】活动状态从 Running 变为 Paused，显示触发规则、时间和影响范围。

【口播】

现在库存降到了停止阈值，活动自动暂停。

这一步很重要。真正进入业务的 Agent 不只是会“开始做事”，还必须知道什么时候停止，把控制权交还给人。

运营可以看到是哪条规则触发、哪个活动版本正在运行、已经产生多少订单，以及恢复活动前需要确认什么。

【观察点】

- 系统业务价值已经落到经营动作；
- 同时展示 Agent 的行动边界，而不是把“全自动”当卖点。

## 第七幕｜真正体现 Loop 价值的是第二次需求

建议时间：25:00—30:00

### 2.18 现场提出变更

【屏幕】回到 Loop Agent Team；记录 V2 变更提出时间。

【口播】

如果演示到这里结束，我们只能证明 Agent Team 做出了一个第一版应用。

但真实业务最常见的状态，是系统刚上线，业务规则就变化了。

现在运营提出一个临时要求：家庭游客不应该看到含酒精商品；需要为家庭客群提供独立的餐饮文创券；成年人只有通过资格校验以后，才能看到含酒精可选项；审批页还必须解释客群资格。

我们把这个变化直接交给原来的 Agent Team。

### 2.19 提交 V2 Prompt

【操作】粘贴以下变更 Prompt。

```text
基于当前 V1 继续迭代，不重建项目。

新增业务规则：
1. 家庭客群只展示“餐饮 + 文创”组合券，不展示含酒精商品；
2. 成年用户只有完成资格校验后，才可看到含酒精可选项；
3. 运营审批页必须展示目标客群、排除客群和资格依据；
4. 已发布活动历史版本不可被覆盖；
5. 为以上规则补充自动化测试，并回归 V1 的审批、幂等、预算、库存和自动暂停能力。

请由 Team Lead 先给出影响分析，再把数据/工作流、前端和测试任务分配给对应 Agent。测试通过后生成 V2 Diff 和发布建议，等待人工确认。
```

### 2.20 强调连续迭代

【屏幕】展示影响分析和各 Agent 接续原任务，而不是重新读取所有背景。

【口播】

这是第五个提效点：连续迭代。

Agent Team 不是从头再做一次。它已经拥有 V1 的业务对象、接口、代码、测试和决策上下文。

Team Lead 先判断这个需求影响哪些地方：客群模型、活动资格规则、游客端卡片、审批页和测试用例。然后只把受影响的部分交给对应 Agent。

数据 Agent 修改资格规则，前端 Agent增加家庭客群展示，测试 Agent同时补充新规则并回归旧功能。这里节省的不是打字时间，而是重新理解项目、重新传递上下文和人工协调依赖的时间。

### 2.21 查看 Diff、回归并发布 V2

【屏幕】展示 V2 关键 Diff、测试结果和版本说明。

【口播】

现在我们不只看页面变化。

请看这次 Diff 同时包含了业务规则、界面解释和测试；历史活动版本没有被覆盖，V1 的审批、预算、库存和自动暂停测试仍然通过。

这说明这次变更不是在页面上增加一个判断，而是作为一项完整业务规则进入了系统。

【操作】人工批准 V2；记录 V2 验收时间。打开游客端，分别用家庭账号和成年已验证账号查看结果。

【口播】

家庭账号现在只看到餐饮文创组合；通过资格校验的成年账号才能看到相应可选项；审批页也保留了客群依据。

到这里，Loop Agent Team 完成了从第一次交付到第二次业务迭代的完整闭环。

【兜底】

如果 V2 未能在舞台窗口内完成，不要宣布成功。展示当前任务、已经完成的影响分析和测试状态，再切换到彩排 Checkpoint 展示预期结果，并明确哪些部分来自 Checkpoint。

## 3. 25 分钟裁剪版

如果现场只有 25 分钟，按以下方式裁剪：

| 时间 | 内容 | 保留重点 |
|---|---|---|
| 0—2 分钟 | 开场和演示边界 | 现场真实内容与预置内容 |
| 2—5 分钟 | 业务事件与主 Prompt | 为什么需要 Team |
| 5—10 分钟 | 计划、并行和共享交付物 | 三个核心提效点 |
| 10—13 分钟 | 测试、人工门禁和 V1 | 独立验收 |
| 13—18 分钟 | 促销审批、执行和暂停 | 系统业务价值 |
| 18—22 分钟 | V2 变更、Diff 和回归 | 连续迭代，绝不能删除 |
| 22—25 分钟 | 实测计分板和收束 | 不宣称预设倍数 |

压缩原则：

- 第一轮任务可在开场前启动，但必须展示真实任务、产物和时间；
- 可以减少业务背景数字和页面浏览；
- 可以只展示一条真实测试；
- 不要删除 V2 变更，因为“持续迭代”比“第一次生成”更能体现 Loop；
- 不要删除现场计分板，否则“提效”只剩主观感受。

- 主持人说“应用完成，业务还没有完成”时，切换运营驾驶舱；
- 主持人说“真正体现 Loop 价值的是第二次需求”时，返回 Loop；
- 主持人说“回到今天的标题”时，切到现场计分板。

### 5.1 某个 Agent 超时

【口播】

这个任务目前超过了我们彩排时设置的舞台等待窗口。Loop 中已经保留了任务状态和已完成产物。为了不让大家等待，我们切换到同一需求在彩排中产生的 Checkpoint，继续现场完成测试、经营工作流和第二次迭代。

### 5.2 自动化测试失败

【口播】

这里出现了一个真实失败：`[说明失败用例]`。我们不会把“代码已经生成”当作完成。现在由责任 Agent 修复，测试 Agent 会重新运行这个用例和相关回归。如果超出舞台时间，我们会保留失败状态并使用 Checkpoint 继续，但本轮不能记为一次通过。

### 5.3 部署或网络失败

【口播】

当前部署通道不可用，但构建和测试结果已经保留。我们切换到本地预览/彩排版本继续业务演示。这个页面不是刚刚在线部署的结果，我们会把部署失败记录在最后的人工介入次数里。

### 5.4 经营事件流失败

【口播】

实时事件模拟器没有按预期推进。我们切换到同一固定种子的事件快照，继续验证审批和暂停流程。经营数字仍然是模拟数据，不影响对 Loop 任务和代码变更的现场计时。

### 5.5 V2 未按时完成

【口播】

V2 仍在执行。现在我们能确认的是影响分析和已经完成的任务，不能把未完成的工作说成成功。为了展示完整业务结果，我们切换到彩排 Checkpoint；本次计分板会记录 V2 在舞台窗口内没有完成。

## 6. 彩排检查清单

### 6.1 产品和环境

- Loop Agent Team 功能、Agent 数量和权限已经在活动版本验证；
- 主 Prompt 和 V2 Prompt 中的项目名、路径和命令准确；
- 所有 Agent 可以访问同一 Workspace 中必要的产物；
- 数据库、事件生成器、预览环境和演示账号可用；
- Checkpoint 可恢复，不只是在界面中显示已创建；
- 现场机器关闭无关通知、自动更新和密钥输出。

### 6.2 业务验收

- 未审批活动不能发布；
- 重复领券只有一张有效券；
- 预算和库存阈值可稳定触发；
- 实验组和对照组分配固定；
- 家庭账号与成年已验证账号显示不同内容；
- 历史活动版本没有被 V2 覆盖；
- 所有模拟数字有醒目标识。

### 6.3 舞台节奏

- 至少完成 5 次全链路彩排；
- 记录每次 V1、V2、测试、部署和恢复实际用时；
- 准备标准版与 25 分钟版两个任务启动点；
- 屏幕字号可以让后排看清任务名、测试状态和核心数字；
- 任何等待超过 20—30 秒时，主持人都有对应讲解内容；
- 不为了等 Agent 而重复解释同一概念。

## 7. 可直接放在结束页的文案

标题：**从“一个 Agent 写代码”到“一个 Agent Team 交付业务”**

左侧：Loop Agent Team

- 把模糊需求变成可验收任务；
- 让可并行工作同时推进；
- 让 Agent 围绕共享产物交接；
- 用独立测试和人工门禁控制质量；
- 在原工作现场上持续迭代。

右侧：智能营促销系统

- 把客流、订单、库存和预算变成当前经营事实；
- 把促销建议变成可审批的业务行动；
- 把执行结果变成可比较、可复盘的经营反馈。

结束金句：

> **高效开发，不是更快地产生代码，而是更短地走完“理解—协作—验证—交付—迭代”的全过程。**
