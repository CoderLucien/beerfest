# 平凯 Loop Workshop：体验 Agent Team 带来的高效开发方式

## 啤酒节智能营促销系统 Demo Show Script V2

建议时长：标准版 32—35 分钟，可压缩为 25 分钟  
修订依据：Loop 官方“设计智能体阵容”“Agent Team”“多智能体协作实战”“如何与智能体协作”文档  
场景性质：合成业务场景，不代表国际啤酒节官方系统  
脚本目标：按照 Loop 实际协作模型，展示 Agent Team 如何完成需求澄清、架构设计、开发、测试、Review、发布和第二轮迭代

> 方括号中的屏幕、操作、观察和兜底提示不需要念出。Loop 按钮名称应在活动版本完成一次逐项核对后替换为准确 UI 文案。

---

## 0. 对照官方文档后的关键修订

原 V1 脚本把团队拆成需求、数据、前端、后端、测试等多个 Agent，容易给观众造成“Agent 越多越高效”的印象。按照 Loop 官方建议，本次 Demo 应改成一个最小且职责清晰的三人 Agent Team。

### 0.1 最小 Agent Team

| Agent | Team 角色 | 职责 |
|---|---|---|
| `solution-architect` | Leader | 理解需求、架构设计、任务拆解、技术决策、代码 Review |
| `fullstack-developer` | Member | 数据模型、后端工作流、前端页面、Bug 修复和构建 |
| `qa-reviewer` | Member / Reviewer | 测试准备、API/集成测试、Bug 复现、回归和测试报告 |

这样设计的原因：

- 官方建议第一次使用从少量、职责清晰的智能体开始；
- Agent Team 推荐从 2—3 个角色起步；
- 设计、实现、测试是本项目真实、长期存在的三类职责；
- 前后端和数据仍属于同一个交付物，现阶段不值得继续拆成更多 Agent；
- `qa-reviewer` 与实现 Agent 分离，才能体现独立验收。

### 0.2 使用职责名，不使用抽象人设

现场不要把 Agent 命名为“智慧大脑”“经营专家”“超级程序员”。名称必须让观众一眼知道应该把什么工作交给谁。

### 0.3 `@Agent Team` 是一次明确派工

普通频道消息不会自动唤醒 Team。现场必须明确输入：

`@beerfest-dev-team ...`

这次请求由 Team 中的具体 Agent 响应和执行。队长先理解需求，再按职责叫其他成员参与。

### 0.4 Team channel、话题和任务各有分工

- **Team channel**：发起需求、对齐范围、汇总结果；
- **话题 Thread**：围绕一个 Bug、接口争议或 Review 点持续讨论；
- **任务 Task**：记录 owner、状态、验收标准、Checkpoint、Artifact 和 Review 历史；
- **任务讨论**：任务建立后的主要执行和协作位置。

### 0.5 一个根任务，不平铺一堆任务

“交付啤酒节智能营促销系统”是一个交付物，因此先创建一个根任务，再根据架构师拆解增加子任务。V2 客群规则是同一项目的增量交付，作为根任务下的新迭代子任务。

### 0.6 提效不等于所有 Agent 同时开始

架构设计必须先形成共同约束，开发才能稳定实施。可并行的部分包括：

- Developer 实现核心流程时，Reviewer 准备测试环境和用例；
- Developer 修复 Bug 时，Architect Review 其他模块；
- V2 实现时，Reviewer 同步扩充回归矩阵。

Demo 重点是减少等待、交接和返工，而不是强行把每一步并行化。

## 1. Demo 前配置

## 1.1 创建三个 Agent

三个 Agent 建议部署在同一台已验证 Machine 上，降低网络、权限和运行环境差异。

### `solution-architect`

建议角色描述：

```text
你是本团队的软件架构师和 Agent Team Leader，负责：
1. 理解业务需求，明确范围、约束和验收标准；
2. 设计业务对象、状态机、接口与技术架构；
3. 把同一个交付物拆成根任务和可执行子任务；
4. 协调 fullstack-developer 与 qa-reviewer；
5. 进行架构和代码 Review，识别风险并提出修改意见。

工作方式：
- 接到团队请求后先输出需求理解、范围和设计，不立即写实现代码；
- 方案经人类确认后再分派执行；
- 所有关键决策、接口契约和 Review 证据沉淀到任务；
- 不替人类批准生产发布。
```

### `fullstack-developer`

建议角色描述：

```text
你是本团队的全栈开发工程师，负责：
1. 根据已批准的架构和验收标准完成数据模型、API、业务工作流和页面实现；
2. 执行数据库迁移、构建和部署预览；
3. 根据 Review 和测试报告修复 Bug；
4. 交付代码 Diff、构建结果和变更说明。

工作方式：
- 不擅自改变业务规则或降低验收标准；
- 实现完成后在任务中提交 Artifact 和 Review Request；
- 收到 Bug 后说明根因、修改范围和回归影响。
```

### `qa-reviewer`

建议角色描述：

```text
你是本团队的测试与质量 Reviewer，负责：
1. 根据原始验收标准设计 API、集成和业务场景测试；
2. 独立部署或运行测试，检查审批、幂等、预算、库存和自动暂停；
3. 发现 Bug 时记录复现步骤、日志、期望和实际结果；
4. 修复后执行相关回归，并输出最终测试报告；
5. 在任务 Review 中批准或请求修改。

工作方式：
- 不以开发 Agent 的自述代替测试证据；
- 未通过的验收项必须明确标记；
- 不能因为舞台时间而降低测试标准。
```

## 1.2 创建 Agent Team

提前使用 Demo 操作员账号创建：

- Team 名称：`beerfest-dev-team`；
- 第一个成员：`solution-architect`，成为 Leader；
- 后续成员：`fullstack-developer`、`qa-reviewer`；
- Team 职责：负责啤酒节智能营促销系统的设计、实现、测试、Review 和持续迭代。

由 Leader 提交成员职责方案后，演示账号提前完成一次 Approval。正式演示时打开 Team 设置展示职责即可，不在舞台上临时创建 Agent。

重要前置条件：

- Agent Team 归创建者个人使用，必须用创建该 Team 的账号演示；
- 一个 Agent 只能属于一个 Agent Team，彩排环境不得把同一 Agent 移入其他 Team；
- 三个 Agent 的 Machine 和 Runtime 均处于可用状态；
- 如把 Team 用在其他频道，应确认成员都已加入该频道；
- 本次直接使用创建 Team 后生成的 Team channel，减少额外配置。

## 1.3 项目与数据预置

公开说明以下内容已经准备：

- 可运行项目骨架、登录导航和基础 UI；
- 数据库连接与迁移入口；
- 10,000 个合成游客会话、12 个商户、48 个商品和 600 笔历史订单；
- 客流、订单、排队和库存事件生成器；
- 支付、消息、地图和 POS 模拟适配器；
- V0 Checkpoint；
- 固定的构建、测试和预览命令。

现场实际完成：

- 需求澄清和 P0 范围；
- 活动、审批和实验相关模型；
- 智能促销审批工作流；
- 驾驶舱核心模块；
- 关键业务测试和 Review；
- 家庭客群资格规则 V2。

## 2. Loop 中的项目组织

### 2.1 Team channel 主线

用于：

- 第一次 `@beerfest-dev-team` 发起项目；
- Architect 输出设计和拆解；
- 人类批准范围；
- 汇总 V1、V2 里程碑和最终结论。

### 2.2 根任务与子任务

根任务：

`交付啤酒节智能营促销系统 Demo`

根任务描述中保存：

- 业务目标；
- P0 范围；
- 验收标准；
- 架构 Artifact；
- 当前版本、Checkpoint 和预览地址；
- V1/V2 子任务进度。

建议子任务：

1. `V1 核心促销工作流实现`，Assignee：`fullstack-developer`，Reviewer：`qa-reviewer`；
2. `V1 业务场景测试与报告`，Assignee：`qa-reviewer`，由 Architect/人类检查测试范围；
3. `V2 家庭客群资格规则`，现场提出后再创建；
4. `V2 回归与发布 Review`，现场提出后再创建或作为 V2 任务 Review 阶段。

状态沿用 Loop 看板：

`Todo → In Progress → In Review → Done`

### 2.3 话题 Thread

如果测试发现重复领券或库存阈值 Bug，从对应测试消息打开话题，在话题中由 `qa-reviewer` 和 `fullstack-developer` 完成复现、修复和复测；完成后把结论回写任务，不让技术细节刷满 Team channel。

## 3. 标准版逐字脚本

## 第一幕｜高效不是多建几个 Agent

建议时间：0:00—3:00

### 3.1 开场

【屏幕】标题页：**平凯 Loop Workshop：体验 Agent Team 带来的高效开发方式**

【口播】

大家好，欢迎来到平凯 Loop Workshop。

今天我们会现场交付一套啤酒节智能营促销系统，但我希望大家观察的不是一个 Agent 打字有多快，而是三个职责不同的 Agent 能不能像一个开发团队一样完成设计、实现、测试、Review 和第二轮迭代。

按照 Loop 的设计原则，Agent Team 不是 Agent 越多越好。我们只用了三个职责清晰的角色：架构师、全栈开发和测试 Reviewer。

架构师是队长，负责理解和拆解；Developer 负责实现；Reviewer 依据原始验收标准独立测试。大家不需要记住每个 Agent 的名字，只需要 `@beerfest-dev-team` 这个团队入口。

### 3.2 说明边界

【屏幕】显示“预置 / 现场执行 / 模拟数据”。

【口播】

项目骨架、数据库连接、外部接口模拟器和合成数据已经准备。今天现场实际发生的是需求拆解、核心实现、测试、Review 和 V2 变更。

经营数字是模拟的；Loop 中的消息、任务、Artifact、代码 Diff、测试结果和耗时是现场实际产生的。

## 第二幕｜从一个经营事件开始

建议时间：3:00—6:00

### 3.3 业务事件

【屏幕】业务 Brief：A 区、B 区、库存、预算。

【口播】

现在是晚上七点半。A 区热门摊位平均排队二十二分钟，B 区客流低于同时间段基线百分之三十五，B 区还有四百二十份餐饮文创组合需要改善周转，促销预算只剩六千元。

业务负责人要求：不要全场无差别打折。请面向合适客群设计一个错峰促销，通过审批后发布，在库存、退款或预算达到阈值时自动暂停，并用实验组和对照组判断活动是否产生了增量。

这不是一个页面需求。它涉及业务对象、状态机、事务、界面、测试和发布，因此适合交给 Agent Team。

【操作】记录 Brief 确认时间，开始墙钟计时。

## 第三幕｜用 `@Team` 发起一次真正的团队派工

建议时间：6:00—10:00

### 3.4 发送 Team 请求

【屏幕】`beerfest-dev-team` 的 Team channel。

【操作】输入并发送：

```text
@beerfest-dev-team 我们要在现有 beerfest-growth Workspace 中交付“啤酒节智能营促销系统”P0 版本。

业务事件：
- A 区平均排队 22 分钟；
- B 区客流低于基线 35%；
- B 区餐饮文创组合库存 420 份；
- 剩余预算 6000 元。

P0 必须完成：
1. 运营驾驶舱展示客流、排队、库存、订单和预算；
2. 生成夜游错峰组合券：满 88 减 12、最多 500 张、90 分钟有效；
3. 未经人工审批不得发布；
4. 发券时校验资格、重复领取、预算和库存；
5. 库存低于 80、退款率超过 3% 或预算耗尽时自动暂停；
6. 使用实验组与对照组展示转化、净支付 GMV 和优惠成本；
7. 所有页面标注“模拟数据，不代表真实经营结果”。

请 Leader 先完成需求理解、范围排除、架构设计、根任务/子任务建议和可执行验收标准。先不要进入代码实现，等待人工确认方案。
```

### 3.5 解释明确 `@` 的意义

【口播】

这里有一个很重要的 Loop 设计：普通消息不会自动唤醒所有 Agent。只有我们明确 `@beerfest-dev-team`，这条消息才成为一次团队派工。

这样可以减少无关唤醒、成本和抢答，也让所有人知道任务从什么时间、由什么请求正式开始。

### 3.6 查看 Leader 输出

【屏幕】展示 `solution-architect` 的需求理解、范围、对象模型和任务建议。

【口播】

队长没有立刻开始写代码。它先回答：系统要交付什么、明确不做什么、哪些对象和状态必须一致，以及什么条件才算通过。

这一步解决的是传统协作中最昂贵的返工：产品、开发和测试各自理解了一套不同的需求。

现在 Architect 建议使用 Campaign、Campaign Version、Approval、Coupon、Experiment Assignment 和 Workflow Instance 等对象，并把“未审批不可发布”“重复请求只能得到一张有效券”“库存低于阈值自动暂停”写成了可测试条件。

【操作】主持人确认范围和架构。

【口播】

Agent 负责提出方案，人负责确认目标和边界。方案通过以后，我们再进入执行。

## 第四幕｜把聊天沉淀成可追踪任务

建议时间：10:00—13:00

### 3.7 创建根任务

【屏幕】Team channel 任务看板。

【操作】创建一个根任务：`交付啤酒节智能营促销系统 Demo`。把 Architect 输出的目标、验收标准和设计链接放入任务描述或 Artifact。

【口播】

这个项目已经不是一次问答。我们希望随时知道谁在跟、做到哪里、下一步是什么，因此把它沉淀为一个根任务。

Loop 不建议把同一个交付物平铺成很多互不关联的根任务。我们用一个根任务保留项目目标和上下文，再创建实现与测试子任务。

### 3.8 创建并指派子任务

【操作】

- 创建 `V1 核心促销工作流实现`，指派 `fullstack-developer`，指定 `qa-reviewer` 负责发布前 Review；
- 创建 `V1 业务场景测试与报告`，指派 `qa-reviewer`，由 Architect/人类检查测试范围；
- 将根任务和实现任务置为 In Progress；
- 测试任务先保持 Todo，Reviewer 可提前准备。

【口播】

任务不是一张标题卡。后续的验收条件、执行讨论、Checkpoint、Artifact 和 Review History 都会留在这里。

Developer 得到的是结构化实现任务，Reviewer 得到的是独立测试责任。Architect 继续负责接口和代码 Review。

## 第五幕｜设计、实现、测试形成协作循环

建议时间：13:00—20:00

### 3.9 开始实现

【屏幕】实现子任务的 Agent Live/任务讨论与 Artifact 区域。

【口播】

现在 Developer 开始实现数据模型、审批工作流、驾驶舱和发券约束。Reviewer 同时准备测试环境和业务用例，Architect 可以检查接口契约和关键事务设计。

这是真正有意义的并行：实现和测试准备可以重叠，但它们仍然围绕同一份验收标准和同一个根任务工作。

### 3.10 展示 Artifact 和 Checkpoint

【屏幕】展示架构 Artifact、实现 Diff 或当前 Checkpoint。

【口播】

Agent 之间共享的不是一句“我做完了”，而是实际产物。

架构设计成为 Artifact，代码和迁移进入 Workspace，阶段状态形成 Checkpoint。Reviewer 使用这些产物进行验证，不需要人把聊天内容重新整理后再转发。

这减少的是上下文重建和交接损耗。

### 3.11 Developer 发起 Review

【操作】实现完成后，Developer 在任务中提交代码/预览 Artifact 和 Review Request，把状态推进到 In Review。

【口播】

代码生成不是任务完成。Developer 现在提交 Review Request，并附上代码、构建结果和预览证据。

Review 不是把看板状态改成 In Review 就结束，而是需要 Reviewer 依据验收标准批准或请求修改。

### 3.12 展示测试与 Bug 循环

【屏幕】Reviewer 的测试报告。如果现场发现真实 Bug，优先使用真实结果。

【口播——存在 Bug】

Reviewer 发现了一个问题：`[按现场结果描述]`。

我们从这条测试消息打开一个话题，让复现、修复和复测在局部上下文里继续，不刷满 Team channel。Bug 同时保留在任务 Review 证据中。

【操作】在话题或任务讨论中明确 `@fullstack-developer` 修复；修复后 `@qa-reviewer` 重新验证。

【口播】

提效不是永远不出错，而是问题更早被独立角色发现，修改责任明确，修复以后可以回归，而不是到演示或生产现场才暴露。

【口播——首轮全部通过】

本轮所有 P0 用例首轮通过。我们依然保留独立 Review，因为“这次通过”不意味着实现 Agent 可以跳过质量门禁。

### 3.13 人类批准 V1

【屏幕】测试报告、Review 决定、通过的验收项和未覆盖风险。

【口播】

现在我们看的是证据：未审批活动不可见、重复领券保持幂等、预算和库存一起校验、库存达到阈值后自动暂停。

Reviewer 给出通过结论以后，最终发布仍然由人确认。

【操作】批准 Review 和发布；将 V1 任务置为 Done；保存 V1 Checkpoint；打开预览并记录 V1 时间。

## 第六幕｜让交付出来的系统完成一条经营工作流

建议时间：20:00—25:00

### 3.14 运行经营事件

【屏幕】运营驾驶舱，播放固定种子的合成事件流。

【口播】

应用已经交付，但系统价值还没有被证明。

晚高峰事件出现以后，系统生成“夜游错峰组合券”：面向合适客群满八十八减十二，最多五百张，有效期九十分钟，并受六千元预算和库存约束。

### 3.15 人工审批

【屏幕】活动建议卡和审批证据。

【口播】

Agent 不是只写一句促销文案。审批人可以看到为什么行动、使用了哪些数据、触达谁、排除谁、最多花多少钱、什么条件下停止，以及最后怎样比较实验组和对照组。

Agent 可以生成方案，但改变业务状态以前，必须经过规则和人的审批。

【操作】批准活动；切换游客 H5，演示符合资格用户领券和模拟下单。

### 3.16 自动暂停

【操作】推进事件，使库存低于 80 或退款率超过 3%。

【屏幕】Campaign 从 Running 变为 Paused，显示触发规则、活动版本和影响。

【口播】

现在停止条件被触发，活动自动暂停。

一个能进入业务的 Agent 不只需要知道怎样开始，还要知道什么时候停止，并把证据和控制权交还给人。

### 3.18 影响分析和增量任务

【屏幕】Architect 输出受影响的客群模型、活动资格、游客端、审批页和测试矩阵。

【操作】人工批准影响分析；创建 `V2 家庭客群资格规则` 子任务，指派 Developer；指定 `qa-reviewer` 为 Reviewer。

### 3.19 V2 Review 和发布

【屏幕】V2 Diff、回归结果和 Review History。

【口播】

这次 Diff 同时包含资格规则、页面解释和测试。Reviewer 不只测试新页面，还回归 V1 的审批、预算、库存和自动暂停。

历史活动版本没有被覆盖，说明这是一项完整的业务规则变更，而不是临时在页面里加一个判断。

【操作】批准 V2；打开家庭账号和成年已验证账号对比；记录 V2 验收时间。

## 6. 失败与兜底

### 6.1 Team 无响应

检查顺序：

1. 消息是否真的明确 `@beerfest-dev-team`；
2. 演示账号是否为 Team 创建者；
3. Team 成员是否可用；
4. Machine 和 Runtime 是否在线；
5. 当前 Agent 是否正在执行另一个任务。

如果只是优先级发生变化并确实需要打断当前运行，可对已经发送的可见消息使用“加急”；不要把每条新消息都设为加急。

### 6.2 Agent 超出舞台等待时间

【口播】

当前任务超过了彩排时设置的舞台等待窗口。Loop 已经保留任务状态、Artifact 和 Checkpoint。为了不让大家等待，我们切换到同一需求在彩排中产生的 Checkpoint；后续 Review、经营工作流和 V2 继续现场执行。

不得把 Checkpoint 说成刚刚完成的结果。

### 6.3 测试失败

【口播】

这里出现了一个真实失败：`[失败用例]`。Developer 需要修复，Reviewer 需要重新验证。本轮不能因为舞台时间记成通过；如果必须切换 Checkpoint，最终计分板仍然记录这次失败和人工介入。

### 6.4 部署失败

【口播】

当前部署通道不可用，但任务中的代码、构建和测试证据仍然保留。我们切换到本地预览或彩排 Checkpoint 继续业务演示，并把部署失败计入现场结果。

### 6.5 V2 没有完成

【口播】

V2 仍在执行。现在可以确认的是影响分析和已完成任务，不能宣布 V2 已交付。为了让大家看到完整预期结果，我们切换彩排 Checkpoint；现场计分板会明确记录 V2 没有在舞台窗口内通过验收。

## 7. 彩排检查清单

### Agent Team

- Demo 操作员是 `beerfest-dev-team` 创建者；
- `solution-architect` 是第一个成员并标记为 Leader；
- 三个成员的职责已经通过 Approval 并保存；
- 三个 Agent 没有被错误加入其他 Team；
- Machine、Runtime、模型和工作目录实际可用；
- 直接 `@beerfest-dev-team` 能触发成员；普通消息不会被误认为已派工。

### 任务与 Review

- 根任务、子任务、Assignee 和 Reviewer 创建流程已跑通；
- 状态可以完成 Todo、In Progress、In Review、Done 流转；
- Artifact、Checkpoint 和 Review Request 在当前版本可见；
- Bug 话题可以回写任务；
- 测试 Agent 可以访问构建产物和测试环境。

### 业务流程

- 未审批活动不可发布；
- 重复请求只产生一张有效券；
- 库存、预算或退款阈值可稳定触发暂停；
- 家庭账号和成年已验证账号显示不同内容；
- V2 不覆盖历史活动版本；
- 所有经营数字有“模拟数据”标识。

### 舞台节奏

- 至少完成 5 次完整彩排；
- 记录每次 V1、V2、Review、部署和 Checkpoint 恢复耗时；
- 等待超过 20—30 秒时有对应讲解；
- 准备 35 分钟和 25 分钟两个启动点；
- 不预先填写提效倍数或经营 ROI。

## 8. 官方文档依据
