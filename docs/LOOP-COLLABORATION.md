# Loop 多 Agent 丝滑协作实践总结

> 编制：leader-cc-air3 | 日期：2026-08-17
> 来源：啤酒节智能营销系统项目的全流程协作复盘（5 Agent × 40+ 任务 × 25+ 轮迭代）

---

## 1. 组织与角色：单一职责，先定边界

| 角色 | 唯一职责 | 明确不做 |
|------|---------|---------|
| leader（PM） | 需求拆解、任务分配、进度同步、验收编排、决策上报 | 不重复 RD 开发 / QA 测试工作 |
| RD | 开发 + 自检 + PR 交付 | 不直接部署上线 |
| QA | 用例设计 + 验证 + 放行结论 | 不修改代码 |
| Dveops | 部署 + 线上验收 | 不在未放行时部署 |
| Ops | 数据分析 + LLM 质量评分 | 不替代 QA 测试 |

**关键**：职责写入 Team 配置（roleOverlayPrompt），成员被唤醒时自动携带职责上下文，不需要每次任务重复交代背景。

## 2. 任务编排：一个需求 = 一个线程

- **线程根消息即需求**：用户 @ 相关成员发起，根消息自带验收意图
- **@mention 精确派单**：谁负责就 @ 谁，不群发
- **线程内闭环**：开发/测试/部署/验收全过程留痕在一个线程，任何人可回看完整决策链
- **任务看板兜底**：多阶段大任务用 task board（status: todo → in_progress → in_review → done）+ assignee 字段
- **milestone checkpoint**：长任务每 5-10 分钟或每完成一个里程碑报告一次：「完成什么 / 下一步 / 有无阻塞」

## 3. 沟通协议：反应即确认，不刷屏

| 场景 | 动作 |
|------|------|
| 收到任务 | 👌 反应（不是"收到"两个字） |
| 完成 | ✅ 反应 + 一句话结果 |
| 同意/通过 | 👍 反应 |
| 正在处理 | ⏳ 反应 |
| 阻塞 | 明确说出卡在哪、需要谁的什么输入 |

**反模式**：acknowledgment 式纯文本（"好的""收到"）会淹没真正信息；状态报告与结果报告分开发，进度不等于完成。

## 4. 交付规范：附件 + diff 范围 + 自检

- **交付走附件**：完整文件以 attachment 传递，不贴大段代码
- **变更说明三要素**：改了哪几处 / 每处为什么 / diff 范围（便于 QA 精确核对）
- **交付前自检**：RD 提交前 `go build` / `node --check` 通过；QA 复验时 diff 精确到行，确认「仅改预期行、无漂移」
- **代码评审**：代码变更走 GitHub PR + review；docs 变更可直接合并

## 5. 验收标准量化：三层验证 + 七道门禁

**三层验证**（QA 核心方法，成本低、拦截率高）：
1. 静态审查 — diff/参数/文案核对
2. 自动化脚本 — 模拟器、loadtest、数值模拟
3. 浏览器实测 — 真实环境操作与渲染验证

**七道验收门禁**（智能问数项目实例）：
L1 数据精确匹配率 ≥95% / L2 分析可接受率 ≥80% / L3 防虚构率 100%（不可妥协）/ 意图分类 ≥90% / 前端 UI 100% / 回归 100% / 延迟阈值

**部署验收标准**：served 内容与交付物全等（diff/md5）、关键参数命中、公网可达、零页面 JS 错误。QA 在部署后必须做**线上生效复验**，而不是部署即完成。

## 6. 缺陷闭环：三次确认，杜绝漂移

```
RD 修缺陷 → QA diff 精确核对「仅改预期行」 → 复验放行 → Dveops 部署 → QA 线上生效复验
```

每轮迭代固定跑回归用例（旧功能不受新接口影响），跨模块数据口径一致性比对（偏差 <0.1）。

## 7. 记忆与沉淀：让下一个会话少走弯路

- **记忆索引（MEMORY.md）**：索引 + 聚焦详情文件，只存未来可复用的偏好/决策/项目事实
- **项目记忆**：待决策项（如「站桩可通关」）、审批状态（requestId）、CLI 正确用法——这些是代码里查不到的上下文
- **收尾总结**：项目结束写 PROJECT-CLOSING-SUMMARY（交付成果/架构决策/质量数据/经验沉淀），为下个项目提供模板

## 8. 实战问题案例与经验教训

> 以下均为本项目真实踩过的坑，按类别整理为「现象 → 根因 → 对策」。

### 8.1 协作与沟通类

| 案例 | 根因 | 对策 |
|------|------|------|
| 高活跃线程中发消息报「Target context outdated」 | 消息流推进后本地上下文过期 | 先 `message_history_read` 读取线程最新状态再重试；重要消息重试直至送达 |
| 游戏包部署时悄悄混入 checkout 三项修复 | RD 基于最新 rebase 交付，变更说明未列出附带内容 | 交付说明必须声明「基于哪个基线 + 附带哪些变更」；QA/Dveops 核对 diff 时确认无未申报改动 |
| 多个 agent 同时对同一需求响应 | 派单未精确到人 | 任务创建即指定 assignee；非负责人以反应确认代替动手 |

### 8.2 开发类（同一参数多处硬编码 → 漂移）

| 案例 | 根因 | 对策 |
|------|------|------|
| JS 已改 GAME_DURATION=30，但 HTML 初始显示仍是 45s | 参数在 JS 与 HTML 两处硬编码 | **参数单一来源**：一处定义、其他处动态引用（`GAME_PASS_SCORE` 动态渲染后，改通关线不再漂移） |
| 待机画布写死「≥20分赢优惠券」，通关线早已改 15 | 文案硬编码未随逻辑更新 | 文案尽量动态引用配置；QA 静态审查专项核对「硬编码数字与逻辑一致性」 |
| 问不存在的券种返回 `{issued}` 字面量 | 模板占位符在空数据时未兜底 | 空数据路径必须有兜底文案（「未找到该券种数据」），模板变量不允许泄漏到响应 |
| 「核销率最低的券」答错 | 代码假设数据升序排序，实际未排序 | 不要依赖隐含排序假设；遍历求 min/max，或显式排序 |
| 120Hz 高刷屏游戏双倍速 | 位移按帧累加，未做帧率归一 | 所有动画/位移用 `speed * dt * 60` 帧率无关化，60/120Hz 同 seed 模拟验证 |

### 8.3 测试类（断言与基准的陷阱）

| 案例 | 根因 | 对策 |
|------|------|------|
| ARPU loadtest 误报 FAIL | 脚本以 Dashboard 新字段为基准，但该字段尚未填充，API 实际是对的 | **基准数据独立核实**：ground truth 不从被测系统的另一个端点取，与数据库直接核对 |
| 告警判断题误报 | 断言死抠关键词（"正常/未告警"），API 回答更完整反而失配 | 断言关注语义等价而非固定词表；答案更有价值时修订用例而非改代码 |
| 提速后「站桩可通关」未被发现 | 只测了判定与计分，没测「不动也能赢」的玩法漏洞 | 测试要包含**玩法对抗视角**（bot 挂机模拟），发现的问题标注「既有问题 vs 本次引入」 |

### 8.4 部署与运维类

| 案例 | 根因 | 对策 |
|------|------|------|
| 页面 Empty reply | 容器状态异常（nginx 重建后容器未就绪），非代码问题 | 线上异常先 `docker ps` 查容器状态再怀疑代码；Dveops 与 RD 分工排查 |
| 长请求 504 | nginx proxy timeout 默认值太小 | 超时参数按最长请求特征调大（300s），部署配置随功能演进同步评审 |
| 部署后才发现内容不一致 | 缺少部署验收标准 | 固定验收动作：served 与交付物 diff/md5 全等 + 关键参数命中 + 零页面 JS 错误 + QA 线上生效复验 |

### 8.5 性能类

| 案例 | 根因 | 对策 |
|------|------|------|
| 确定性问题 p95 延迟 2111ms 超 1000ms 门禁 | LLM 意图路由调用是主瓶颈 | 高频映射加短 TTL 缓存（券种名→模板）；门禁不通过也要区分「阻塞」与「非阻塞项」并明确记录 |

**总原则**：每个 bug 修完不是终点——回填「为什么会发生、怎么防止再发生」到文档/记忆，同类问题不出现第二次。

## 9. 丝滑协作 Checklist

- [ ] 职责已写入 Team 配置，成员各司其职、互不重复
- [ ] 一个需求一个线程，根消息清晰、@ 精确派单
- [ ] 用反应代替确认文本，里程碑 checkpoint 不中断工作流
- [ ] 交付附完整变更说明 + diff 范围，交付前自检通过
- [ ] 验收门禁量化（数字阈值），三层验证覆盖
- [ ] 部署后有线上生效复验，非"部署即完成"
- [ ] 敏感信息（部署 IP、密钥）不入库，文档用占位符
- [ ] 项目收尾有沉淀总结，待决策项有明确 owner 和去向

---

**一句话总结**：丝滑 = 角色边界清晰 × 沟通低噪音（反应+checkpoint）× 交付可核对（diff 范围+自检）× 验收可量化（门禁+三层验证）× 闭环有复验（线上生效确认）× 上下文有沉淀（记忆+收尾总结）。
