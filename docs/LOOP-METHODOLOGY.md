# LOOP 多 Agent 软件开发实践方法论

> 版本 v1.0 | 编制：leader-cc-air3 | 日期：2026-08-17
> 来源：啤酒节智能营销系统项目全流程实证（5 Agent × 40+ 任务 × 25+ 轮迭代）
> 定位：基于 LOOP 多 Agent 协作平台的软件交付体系化方法，可直接复用于同类项目

---

## 0. 方法论总览

```
组织模型（谁做）
    ↓
流程模型（怎么做）  ←→  质量模型（做到什么程度才算好）
    ↓                      ↓
沟通协议（如何高效同步）  度量与复盘（如何持续变好）
    ↓
工具链（用什么承载）     模板与清单（如何落地）
```

六层结构自洽：组织定义角色边界，流程串联生命周期，质量给出门禁阈值，沟通降低协作噪音，度量驱动复盘，模板保证可复制。

## 1. 组织模型

### 1.1 标准角色五件套

| 角色 | 唯一职责 | 明确不做 | 关键交付物 |
|------|---------|---------|-----------|
| **Leader（PM）** | 需求拆解、任务分配、进度同步、验收编排、决策上报 | 不重复 RD 开发 / QA 测试 | 任务拆解单、闭环汇报 |
| **RD** | 开发 + 自检 + PR 交付 | 不直接部署 | 变更文件 + diff 说明 |
| **QA** | 用例设计 + 三层验证 + 放行结论 | 不修改代码 | 测试报告 + 放行/阻塞结论 |
| **Dveops** | 部署 + 线上验收 | 不在未放行时部署 | 部署记录 + 生效验证 |
| **Ops（可选）** | 数据分析 + LLM 质量评分 | 不替代 QA 测试 | 数据报告 + 评分表 |

### 1.2 职责配置落地

- 职责写入 Team 配置（roleOverlayPrompt），成员唤醒即带上下文，零重复交代
- 任务创建即指定 assignee，杜绝多人抢同一需求
- 派单精确 @ 到人，非负责人以反应确认代替动手

## 2. 流程模型（全生命周期八步）

| 步骤 | 输入 | 输出 | 负责人 |
|------|------|------|--------|
| ① 需求受理 | 用户需求 | 需求理解确认（含数据边界） | Leader |
| ② 方案选型 | 需求 + 约束 | 2-4 个方案对比表 + 推荐 | Leader + 全员 |
| ③ 任务拆解 | 确认方案 | 任务清单（粒度 ≤ 半天）+ assignee + 验收标准 | Leader |
| ④ 开发交付 | 任务 | 变更文件 + 变更说明三要素（改了什么/为什么/diff 范围） | RD |
| ⑤ 三层验证 | 交付物 | 测试报告（静态/自动化/实测）+ 放行结论 | QA |
| ⑥ 部署验收 | 放行结论 + 交付物 | 部署记录 + served==交付物全等比对 + 关键参数命中 | Dveops |
| ⑦ 线上复验 | 部署完成 | 线上生效复验报告（非"部署即完成"） | QA |
| ⑧ 复盘沉淀 | 全过程 | 收尾总结 + 问题案例回填 + 记忆更新 | Leader |

**关键纪律**：
- 每步有明确验收物才进入下一步，放行是下一步的准入门槛
- 长任务每 5-10 分钟 milestone checkpoint：完成什么 / 下一步 / 有无阻塞
- 阻塞时明确说出「卡在哪、需要谁的什么输入」，不空等

## 3. 质量模型

### 3.1 三层验证法（QA 核心）

1. **静态审查**：diff/参数/文案/硬编码核对，成本最低、最先执行
2. **自动化脚本**：模拟器、loadtest、数值模拟、完美 bot 千局模拟
3. **浏览器/环境实测**：真实环境操作、渲染、全链路验证

### 3.2 七道验收门禁（按项目定制阈值）

| 门禁 | BeerFest 实证阈值 | 性质 |
|------|------------------|------|
| L1 数据精确匹配率 | ≥95% | 精确性 |
| L2 分析可接受率 | ≥80% | 智能质量 |
| L3 防虚构率 | 100%（不可妥协） | 诚实底线 |
| 意图/路由分类准确率 | ≥90% | 稳定性 |
| 确定性延迟 | p95 <1000ms | 性能 |
| 前端 UI 通过率 | 100% | 体验 |
| 回归通过率 | 100% | 兼容性 |

不通过也要分级：**阻塞项**（L3、回归、UI）必须修复才上线；**非阻塞项**（如延迟 2111ms）记录留待下轮迭代，不阻塞发布。

### 3.3 部署验收标准（固定动作）

served 内容与交付物 diff/md5 全等 → 关键参数命中 → 公网可达 → 零页面 JS 错误 → QA 线上生效复验。

### 3.4 缺陷闭环（三次确认杜绝漂移）

```
RD 修复 → QA diff 精确核对「仅改预期行」→ 复验放行 → Dveops 部署 → QA 线上复验
```

## 4. 沟通协议

### 4.1 线程模型

- **一个需求 = 一个线程**：根消息即需求，全部过程留痕，可回看完整决策链
- 高活跃线程发消息可能报「context outdated」：先读线程历史再重试，重要消息确认送达

### 4.2 反应语义（降低噪音）

| 反应 | 语义 |
|------|------|
| 👌 | 收到任务 |
| ⏳ | 正在处理 |
| ✅ | 完成 |
| 👍 | 同意/通过 |
| 💯 | 强烈同意 |

### 4.3 报告纪律

- 进度 ≠ 完成：milestone 报告是过程信息，完成报告才是结果信息
- 结果报告一句话结构：交付什么 / 验证数据 / 下一步
- 禁止 acknowledgment 式纯文本（"收到""好的"），用反应代替

## 5. 工具链

| 工具 | 用途 | 要点 |
|------|------|------|
| Loop 线程 | 需求→验收全流程留痕 | 根消息=需求，@精确派单 |
| Loop 任务看板 | 多阶段大任务 | status 流转 + assignee |
| Loop 记忆库 | 跨会话上下文 | 索引 MEMORY.md + 聚焦详情文件；存偏好/决策/待决项，不存代码可推导内容 |
| GitHub PR + review | 代码变更评审 | docs 变更可直接合并 |
| 附件交付 | 完整文件传递 | 附 diff 范围说明 |

## 6. 风险管理

### 6.1 诚实数据边界（AI 系统专项）

- 系统无某维度数据时，明确声明「当前无该维度数据」+ 最近似参考，绝不虚构
- 分析类回答强制标注「推测/分析」，与精确数据视觉区分
- 空数据兜底文案，模板变量不允许泄漏

### 6.2 安全与开源

- 敏感信息不入库：部署 IP、数据库账号、API key 一律占位符或 env 变量
- 硬编码参数单一来源：动态引用配置，防止漂移
- 开源前检查：敏感扫描 + 可构建验证 + git 历史清理

### 6.3 回滚与灰度

- 静态页 inode 覆盖热部署，回滚 = 覆盖回旧文件
- 部署前确认回滚方案存在

## 7. 度量与复盘

### 7.1 度量采集

- 每轮迭代记录门禁数据（L1/L2/L3、延迟、通过率），形成趋势
- 缺陷记录三元组：现象 → 根因 → 对策，回填问题案例库

### 7.2 复盘节奏

- 每任务收尾：一句话复盘（哪里顺、哪里卡）
- 每项目收尾：PROJECT-CLOSING-SUMMARY（成果/决策/质量数据/遗留项/经验沉淀）
- 方法论修订：实证中发现的新模式回写本文档

## 8. 模板与清单

### 8.1 任务拆解模板

```
任务标题：[模块] 一句话目标
负责人：@xxx | 验收标准：可量化描述
依赖：无 / 等 #xx 完成
```

### 8.2 交付说明模板

```
改动清单：文件 + 行号 + 改了什么
基线说明：基于哪个 commit/线上版本
附带变更：无 / 列出
自检：go build / node --check 结果
```

### 8.3 测试报告模板

```
通过项：n/m（表格：检查项/方法/结果）
缺陷：编号 + 现象 + 严重级（P1 阻塞 / P2 建议修）
观察项：非本次引入、待决策
结论：放行 / 修复后放行 / 阻塞
```

### 8.4 开源发布前检查清单

- [ ] 敏感扫描通过：无硬编码密码/IP/API key（含 git 历史）
- [ ] 从零构建验证通过：干净环境按 README 可起完整系统
- [ ] .env.example 覆盖全部必需变量，占位符模式
- [ ] README 含架构图 + 快速开始 + API 概览 + 文档导航
- [ ] LICENSE 就绪
- [ ] 收尾总结与协作方法论文档齐备
