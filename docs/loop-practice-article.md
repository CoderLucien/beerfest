# 一场啤酒节，检验一支多 Agent 团队：Loop 如何让营销系统敏捷上线

啤酒节开幕前两周，业务部门的玩法还在变：主会场要满减，精酿专场要买一送一，音乐嘉年华的套餐价格迟迟定不下来。放在传统开发节奏里，每一个变更都要走一遍「排期—开发—测试—上线」的完整流程，以周为单位。等系统改完，节都过完了。

这不是假设场景，而是一个真实项目：啤酒节智能营销促销系统（GitHub: CoderLucien/beerfest，MIT 开源）。它由平凯 Loop 多 Agent 协作平台上的一个五人智能体团队开发交付，覆盖活动管理、促销规则引擎、优惠券发放核销、客户分群、A/B 实验、运营看板等完整能力。这篇文章记录它的开发实践：**业务为什么需要敏捷营销系统、如何使用 Loop 高效开发、以及 Loop 带来的价值**。

## 一、业务为什么：快速变化的 to-C 营销，等不起传统开发节奏

to-C 营销有三个鲜明特征：**节点密集、玩法多样、变化极快**。一场大型节庆活动往往包含多个并行子活动，每个子活动挂着折扣、优惠券、套餐等十几条促销规则；满减力度、活动时间、适用分群随时可能调整。业务部门需要的是「今天提需求，明天能上线」，而不是在漫长的排期里等待。

传统开发模式下，这类需求几乎必然滞后：一个促销规则的改动要跨产品、研发、测试多个环节排期；多个活动并行时版本互相等待；上线后发现问题又进入新的变更周期。营销窗口稍纵即逝，系统响应速度直接决定了促销活动的成败。这正是「敏捷营销系统」的由来——让技术交付的速度跟上营销变化的节奏。

还有一个更普遍的瓶颈：个人使用 AI 助手提速已经很明显，但一到多人协作，需求、文档、意见还是靠通讯软件传来传去、人工搬运，沟通与等待反而成了新的瓶颈。营销系统的开发正是典型的多角色协作工程——业务提需求、研发写代码、测试做验收、运维管上线，任何一环的搬运和等待都在消耗营销窗口。

这种场景对系统提出了明确要求：

1. **促销规则可配置**：折扣、优惠券、套餐等规则由运营直接管理，改规则不改代码；
2. **活动全生命周期管理**：活动从草稿、审批、进行中到结束有清晰的状态机（draft → active → paused → ended）；
3. **交易级可靠**：优惠券发放与核销是原子操作，高峰期不能超发、不能重放；
4. **数据驱动运营**：客户分群精准触达、A/B 实验验证策略、运营看板实时洞察；
5. **从零可构建**：任何客户或开发者拿到仓库，都能在短时间内拉起一套完整可用的前后端系统。

啤酒节项目最终交付了 17 个 REST 端点、10 步完整业务流程测试，以及一个覆盖「活动创建 → 促销配置 → 审批 → 发券 → 核销 → 分群 → A/B 实验 → 模拟器 → 运营看板」的全链路演示环境——demo 模版内置 3 个活动、16 条促销，打开即演示。技术栈为 Go 1.22 + Gin、TiDB Cloud Serverless、Redis 7，容器化部署，GitHub Actions 自动化 CI/CD。更重要的是，整个系统按「从零可构建、开源可复现」的标准交付：任何开发者克隆仓库后，照着 README 走两条路径之一（推荐 TiDB Cloud Serverless，或本地 MySQL 8 试玩），一条命令即可拉起完整的前后端系统。

## 二、如何使用 Loop：一个 leader + 四个专业 agent 的分工协作

平凯 Loop 是一个多 Agent 协作平台：人类和多个智能体在频道（Channel）、线程（Thread）、任务板（Task Board）上协同工作，所有上下文留在频道线程里共享——任何成员接手都能回看，不靠私聊转发、不靠文档来回搬运。啤酒节项目的团队由五个智能体组成，各司其职：

| 角色 | 职责 |
|------|------|
| leader（团队负责人/PM） | 需求拆解与任务分配、30 分钟进度同步、跨成员协调、验收编排与闭环汇报、重大决策上报 |
| RD（研发工程师） | Go 后端 + 前端开发；自检通过后交付；代码变更走 GitHub PR + review |
| QA（测试工程师） | 用例设计 + 三层验证（静态审查/自动化/浏览器实测）；缺陷跟踪与复验放行 |
| Dveops（部署运维） | 容器重建/热部署；部署后线上验收（内容全等 + 参数命中）；公网可用性保障 |
| Ops（运营分析师） | 数据分析与 loadtest 自动化；LLM 问答质量抽样评分；运营策略建议 |

职责写入团队配置后，每个 agent 被唤醒时自动携带自己的职责上下文，无需反复交代。人类（项目负责人）只需要做三件事：提需求、做决策、看结果——中间的拆解、开发、测试、部署、验收全部由 agent 团队协作完成。

协作机制上，项目坚持了几个关键约定：

**需求 → 线程 → 任务板一条线。** 每个需求开独立线程闭环讨论，拆成若干任务挂上任务板，每个任务有唯一负责人，状态在 todo → in_progress → in_review → done 之间流转。进展记在任务上，任何成员随时可查，不存在「散落在聊天记录里的需求」。

**依赖链决定流水线顺序。** 不按角色固定顺序，而是按「谁等谁」编排。例如一轮运营问答功能的五个任务（#t72-#t76）按 RD → QA → Dveops 的依赖链推进；接口未部署时 QA 先测必然 404，所以把顺序改成「RD 交付 → Dveops 部署 → QA 测线上」，一次打通。

**验收驱动闭环。** 任何变更以 QA 验收 + 部署实证为准才算完成；同一结论走两条独立验证路径（自动化 + 人工抽样）才采信。代码交付用 patch + 全量归档互证防传输失真，成员不直接推主分支，由 leader 集成后统一推送，并行改动不会互相覆盖。沟通上用 reaction 代替寒暄（👌收到 / 👍通过 / ✅完成），每 30 分钟同步一次进度，噪音极小。

这套机制的要点在于：业务与工程在同一个任务上下文里并行工作——业务提需求，研发交付，测试与运维同步验证，**人做最终判断**。每一轮验收都由项目负责人确认放行，Agent 负责把「搬运行李」的部分全部消化掉。

这套机制的真实效率如何？举一个例子：一次「品牌词统一 + 测试模版扩展多活动」的需求调整，涉及代码变更、生产部署、清库重 seed、QA 终验全链路——**从 18:14 派单到 18:40 QA 终验放行，全程约 25 分钟**。当天晚上，生产站点就已经跑在新口径与新种子数据上。同一模式下还完成了两件更重的工程：生产数据库底座整体切换（TiDB Cloud Serverless 集群迁移，八张业务表重建、健康检查全绿后无缝恢复），以及开源化改造——为了确保「仓库可开源」四个字经得起推敲，团队对 git 全历史做了三轮重写，敏感凭据、服务器 IP、品牌词、个人姓名与邮箱在代码与提交历史中零残留，并让 QA、研发、运维三方独立扫描互证后才放行；README 提供 TiDB Cloud 与本地 MySQL 双路径「从零构建」指南，任何开发者拿到即用。

除了需求驱动的迭代，团队还经历过完整的多轮次实战：从 V1 核心业务能力，到客户分群、A/B 实验、合成数据与业务日模拟器等增量里程碑，再到异常订单检测、促销数据报表、运营问答机器人等运营能力。每一轮都走同一条「线程提需求 → leader 拆解派单 → 开发自检 → QA 验收 → 集成推送 → 生产回归 → 闭环汇报」的流水线，机制越跑越顺。

## 三、Loop 带来的价值

**速度：需求响应从「周」到「小时」。** 五个 agent 并行分工、依赖链编排，人类只需要做决策和确认，重复劳动交给 agent。上文 25 分钟闭环的案例说明：当流程和规范跑顺之后，变更交付的主要时间花在真正的工程动作上，而不是沟通与等待。依赖链编排也让瓶颈显性化——比如一轮运营问答功能开发中，接口尚未部署时测试必然受阻，团队随即把流水线调整为「研发交付 → 部署上线 → 测试线上」，一步打通。

**质量：验收驱动 + 多路径互证。** QA 的静态审查、自动化测试、浏览器实测三层验证，加上 Dveops 的线上实证（文件 md5 全等、接口参数命中），同一结论两条路径交叉印证，让「完成了」三个字有证据支撑。开源前的脱敏验收更是全员参与：leader、QA、RD 三方独立扫描，全树与全历史零命中才放行。生产环境的每次变更同样以证据链收尾——页面逐字节一致、接口返回与种子数据吻合、健康检查全绿，任何成员都能独立复核。

**沉淀：经验变成组织资产。** 项目产出了两份方法论文档：六层体系的方法论（组织/流程/质量/沟通/度量），以及 15 个真实踩坑案例的协作实践总结；README 中还有「基于 Loop 开发入门」章节，新成员照着走就能上手。踩过的坑——比如环境变量位置断裂、作者邮箱泄露等——被写进文档和 agent 记忆，后续轮次自动规避。项目做完，团队的协作能力被显式地固化下来，可以直接复用到下一个项目。

**可复制：客户拿来即用。** 推荐部署路径是 TiDB Cloud Serverless（免费集群即可承载），TLS 加密连接无需下载证书，一条 docker compose 命令拉起完整系统；没有 TiDB 账号也能用本地 MySQL 8 容器一键试玩。从零构建、开源协议、完整文档——这套系统本身就是一个可交付的参考实现：客户拿到的不只是代码，还有一套被验证过的开发与运营方法。

## 写在最后

快速变化的 to-C 营销，需要同样敏捷的营销系统；而多 Agent 协作正在成为新的开发生产力。啤酒节项目的实践证明：明确的职责分工、任务驱动的协作机制、验收驱动的质量闭环，能让一个小型智能体团队以极快的节奏交付生产级系统——并且把过程中的方法沉淀下来，让下一次更快。

Loop 不只让一个人更快：个人使用智能体的效率提升如今已是共识。它更让人和 Agent 把复杂工作真正跑起来——需求、开发、测试、部署、验收这些过去靠人工搬运串联的环节，在共享上下文里并行推进，让一个小团队也能驾驭系统级工程。

项目已开源在 GitHub（CoderLucien/beerfest），欢迎从零构建体验。
